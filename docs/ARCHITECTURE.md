## Topology

| Component | Type | Responsibility | Primary source |
| --- | --- | --- | --- |
| Participants | external | Browsers of signed-in members and link guests | — |
| Web Client | frontend | React 19 SPA: auth, dashboard, projects, meetings, tasks | `client/package.json` |
| Meeting Room | frontend | WebRTC peer mesh, Q&A, polls, per-participant recording capture | `client/src/hooks/useWebRtcMeeting.ts`, `client/src/pages/meetings/MeetingRoom.tsx` |
| Express REST API | backend | 13 route mounts, JWT auth, tenant scoping | `server/src/routes/index.ts`, `server/src/app.ts` |
| AI Post-Processing | backend | Per-speaker FFmpeg → Groq Whisper → OpenRouter, inline after `complete()` | `server/src/services/recording-post-processing.service.ts` |
| Socket.io Signaling | backend | JWT handshake, meeting rooms, SDP/ICE relay, presence, chat | `server/src/socket/socket.ts` |
| S3-Compatible Storage | cloud | Private bucket; browser uploads per-speaker tracks via presigned PUT | `server/src/services/storage.service.ts` |
| MongoDB | database | 14 collections, all organization-scoped | `server/src/models/*` |
| STUN Server | external | ICE discovery for the browser mesh (`stun.l.google.com`) | `client/src/hooks/useWebRtcMeeting.ts` |

**Runtime boundaries:** *Browser (client runtime)* wraps Web Client + Meeting
Room; *Node 22 server process* wraps the API, AI pipeline and signaling.
Storage and MongoDB are reached from the server process only — except the
recording upload, which the browser performs directly against storage (one
presigned PUT per speaker track).

**Deliberately not drawn:** the server-admin control plane (`/v0` and
`/v1/server-admin`), work roles, tasks and user-details — ordinary CRUD behind
the same JWT + tenant-scoping pattern as everything else on the map.

Paths:

- **Main path:** Participants → Web Client → Express REST API → MongoDB
- **Meeting path:** Web Client → Meeting Room → Socket.io Signaling →
  MongoDB (roster / team / project re-check on `meeting:join`)
- **Media path:** Meeting Room ↔ Participants as **peer-to-peer WebRTC**;
  STUN lookup for ICE. Media never touches the server.
- **Recording path:** API presigns a PUT URL per speaker track → the browser
  uploads directly → `complete()` verifies every track with `HeadObject` →
  the inline AI pipeline writes transcript + summary to MongoDB.

## Request & Data Flows

### 1. Authentication (REST)
1. `POST /api/v1/auth/login` → access JWT in the body, rotating refresh token
   in an `httpOnly` cookie.
2. Every subsequent REST call sends `Authorization: Bearer …`;
   `authenticateUser` puts `userId` + `organizationId` into request scope.
3. Every Mongo query filters on that `organizationId` — a foreign tenant's row
   is a `404`, never a leak.

### 2. Real-time meeting (Socket.io + WebRTC)
1. The socket handshake carries the **same access JWT**; an invalid token is
   disconnected before any event handler runs.
2. `meeting:join` re-checks org scope, then creator / roster / team / project
   membership, joins the `meeting:<id>` room, acks the peer list, and
   broadcasts `meeting:peer-joined`.
3. Peers exchange `webrtc:offer` / `webrtc:answer` / `webrtc:ice` — the server
   **relays payloads untouched** to the target's user room. Audio/video flows
   peer-to-peer (Google STUN for ICE); `meeting:state` fans out
   mute/camera/screen/hand changes.
4. `meeting:leave` and disconnect emit `meeting:peer-left`.

### 3. Recording → transcript → summary
1. `POST /api/v1/recordings` creates a `PENDING` record with **one storage key
   per speaker**, derived server-side from org + recording id — never from the
   request.
2. `POST /:id/upload-url` signs a PUT for one speaker's key (repeatable for
   retries).
3. The browser uploads each track **directly** to storage.
4. `POST /:id/complete` runs `HeadObject` per track — the stored object's
   type/size are authoritative. One bad track deletes every track and marks
   the recording `FAILED`; all-good tracks become `READY`.
5. `runPostProcessing` executes inline (single seam, queue-swappable):
   FFmpeg extracts audio → Groq `whisper-large-v3` transcribes **each speaker
   separately** (tracks are never mixed — simultaneous speech garbles a
   transcript) → OpenRouter summarizes with action items, trying a fallback
   chain of free-tier models. A failed stage marks only its own record
   `FAILED`; summarisation can be retried without retranscribing.
6. `GET /:id/transcript` and `GET /:id/summary` serve the results.

## Security Invariants Shown in the Diagram

- **Single token trust:** one JWT authenticates REST and Socket.io alike.
- **Tenant isolation:** org id comes from the verified token, never the body.
- **Private storage:** the bucket has no public reads; presigned GET/PUT URLs
  are the capability, and `storage_key` is never serialized to clients.
- **Server-authoritative media metadata:** `HeadObject`, not the client,
  decides recording type and size — per track.
- **Least-privilege meeting control:** host/moderator checks gate participant
  permissions, start/end, poll creation/close; per-member capability flags
  (mic/cam/screen/chat) live on the roster.

## Regenerating the Diagram

The map is **generated, then restyled** — two steps, in order.

1. Edit the spec: `.archify/architecture-intellmeet-20261015-052329/candidate.json`
   (node positions, connections, cards, and each node's `sources` with current
   file + line evidence — max 3 per node).

2. Regenerate with the archify skill (installed at
   [`.agents/skills/archify/`](../.agents/skills/archify/SKILL.md)):

   ```bash
   node .agents/skills/archify/bin/archify.mjs finalize architecture \
     .archify/architecture-intellmeet-20261015-052329/candidate.json \
     docs/architecture-diagram.html \
     --repo-root . --quality showcase --json
   ```

   A passing receipt proves the `validate`, `deliver`, `check` and real-browser
   `browser-check` gates passed. If a crossing or detour is reported, move the
   offending node before re-running — do not add edges that force one (a
   `meetingRoom → storage` edge crosses the main path; the direct-upload fact
   belongs in a card instead).

3. Re-apply the restyle. `finalize` rewrites the whole file, so the "Ink
   Graphite" layer must be appended again: copy the final
   `<style id="ink-graphite-restyle">` block from the previous artifact
   (`git show HEAD:docs/architecture-diagram.html`) and paste it before
   `</head>` of the regenerated file.

4. Open the file in a browser and confirm: no console errors, no horizontal
   overflow, the nav dock still sits inside the diagram container, and the
   geometry still reads.

Keep the candidate's `sources` line ranges in sync with real code before
regenerating — every claim on the map is backed by one.
